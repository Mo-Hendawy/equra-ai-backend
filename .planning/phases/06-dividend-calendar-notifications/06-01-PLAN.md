<objective>
Deliver the dividend-calendar polling + Expo push notification feature end-to-end. Users get two daily notifications (06:00 + 18:00 Cairo) describing new and updated dividend events on claps.therumble.app; tapping opens a new in-app Notifications tab with the last 10 batches.
</objective>

<scope>

**In scope:**
1. Backend polling + diffing + smart-batched push dispatch
2. SQLite tables for events / tokens / notification history (via MemoryService CREATE TABLE block)
3. Backend HTTP endpoints for token registration, history listing, and manual poll trigger
4. Mobile expo-notifications install, permission flow, token registration with idempotency
5. Mobile segmented Calendar / Notifications view inside DividendCalendarScreen
6. Mobile notification tap handler deep-linking to the Notifications tab
7. EAS scaffolding with placeholder projectId (prod push requires `eas init` by user)

**Out of scope:**
- Per-user filtering by portfolio holdings (tag symbols available for future)
- iOS APNs / Android FCM direct integration (Expo push abstracts this)
- User opt-in toggle (all registered devices receive all batches for now)

</scope>

<pitfall_watch>

- **Source HTML brittle:** mitigated by using The Events Calendar REST API directly (`/wp-json/tribe/events/v1/events`), not scraping the HTML page.
- **Notification spam on busy days:** 5+ changes collapse to a count-only body; 2–4 become a comma-separated symbol list; single changes show the full title.
- **DeviceNotRegistered tokens:** Expo surfaces this error per-ticket; we prune in the same pass as the dispatch.
- **EAS projectId missing in production build:** `registerForPushNotifications` short-circuits if the placeholder `REPLACE_ME_RUN_eas_init` is present, so local dev never POSTs a broken token.
- **Cold-start notification tap:** `getLastNotificationResponseAsync` handled with a 600 ms defer so NavigationContainer is mounted before the navigate call.

</pitfall_watch>
